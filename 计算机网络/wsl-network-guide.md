## 1. 网络是什么：送信的故事

两台电脑之间通信，本质上和**寄信**是一模一样的：

```
你写信 → 写收件人地址 → 投进邮局 → 邮局转运 → 送到收件人手里 → 收件人回信
```

电脑之间的网络通信也是这个流程：

```
你的电脑 → 知道目标地址 → 发送数据包 → 路由器转发 → 到达目标电脑 → 目标电脑回复
```

- 信的内容 = **数据**（网页、文件、聊天消息）
- 收件人地址 = **IP 地址**
- 邮局系统 = **路由器、交换机、网络运营商**

**"三次握手"** 听起来吓人，其实就是：寄信前先确认对方在家——

1. 你打电话："喂，你在家吗？"
2. 对方："在，你能听到我吗？"
3. 你："能听到，我寄信过来了。"

三句话确认双方都能收能发，然后才开始传数据。就这么简单。

## 2. IP 地址：每台电脑的门牌号

每台联网的电脑都有一个 **IP 地址**，格式是四组数字：

```
192.168.1.100
10.0.0.5
172.16.0.3
```

- 路由器会分配给你一个**内网 IP**（家里、公司的局域网）
- 整个网络世界有一个**公网 IP** 系统（互联网上唯一的地址）

**常见误解**：你的 IP 不是全世界唯一的。你家的 Wi-Fi 给电脑分的是内网 IP（如 192.168.x.x），全世界的家庭 Wi-Fi 都在用这组数字——但没关系，因为邮递员（路由器）只在**你们小区**里送信，出了小区就有 NAT（网络地址转换）帮你换包装。

打个比方：内网 IP 就像"3 号楼 502 室"，只在你们小区有意义；公网 IP 就像"北京市朝阳区 xx 路 12 号"，全世界都能定位。

## 3. 127.0.0.1：一个特殊的地址，意思是"我自己"

有个特殊门牌号叫 **127.0.0.1**，它永远指向**当前这台电脑自己**，也叫 **localhost**（本地主机）。

用途：一个程序想和同一台电脑上的另一个程序通信，不用真的把数据发到网络上绕一圈，直接走 127.0.0.1 就行。

**你的代理软件就是这种用法**：

```
代理软件（Clash 等）运行在 Windows 上
监听地址：127.0.0.1:17891
意思是："我在本机的 17891 号房间等着接收请求"
```

## 4. 端口：一栋楼里的不同房间

一台电脑可能同时跑着很多网络服务：

- 网页服务器
- 代理软件
- SSH 服务
- 数据库

它们共用同一个 IP 地址，怎么区分？靠 **端口号**（0–65535）。

```
127.0.0.1:17891
  │        │
  │        └── 端口号 = 17891 号房间（你的代理）
  └── IP 地址 = 本机
```

常见端口约定（就像"餐厅在一楼、健身房在二楼"）：

| 端口 | 服务 |
|------|------|
| 80 | HTTP 网页 |
| 443 | HTTPS 加密网页 |
| 22 | SSH 远程登录 |
| 7890 / 17891 / 1080 | 常见代理软件端口 |

**"端口被占用"** 的意思就是：两家人想住同一间房，先到先得。

## 5. 客户端和服务端：寄信人和收信人

网络通信永远是两方：

- **客户端**：主动发起请求的一方（你的浏览器、curl、apt）
- **服务端**：被动等待、响应请求的一方（Google 的服务器、你的代理软件）

```
客户端（curl）         服务端（代理软件）
     │                        │
     │──── 请求：帮我抓google ──→│
     │                        │
     │←── 响应：网页内容 ────────│
```

**连接被拒绝（Connection refused）** = 你敲了 17891 号房的门，但里面根本没人住（服务没启动）。

**超时（Timeout）** = 门敲了，里面有人应了门铃，但就是不说话（服务挂了、或者网络路径不通）。

## 6. DNS：查门牌号的电话簿

你从来不在浏览器里输入 `142.250.72.14` 来访问 Google，你输入的是 `google.com`。

把名字翻译成 IP 地址的服务就是 **DNS**。它就像 114 查号台：

```
你问：google.com 的门牌号是多少？
DNS 答：142.250.72.14
```

**"DNS 解析失败"** = 查号台打不通。域名没问题，但你不知道往哪寄信。

## 7. IPv4 和 IPv6：新旧两套门牌号系统

**IPv4**（老系统）：`192.168.1.100` 这种四组数字，全球只有约 43 亿个地址。2011 年就用完了。

**IPv6**（新系统）：`2408:8207:2459:8f40:...` 这种很长的新格式，地址数量几乎无限。

问题在于：**新旧系统不兼容**。一个只懂 IPv4 的设备，收到 IPv6 地址会不知所措。

现在很多网站同时提供两种地址。当你的电脑同时懂两种时，它会**优先尝试 IPv6**。

**这就是你 WSL 卡住的深层原因之一**——详情见第 9 节。

## 8. 代理：帮你买海外商品的代购

由于网络管制，中国大陆的网络无法直接访问 Google 等网站。解决方案是**代理**：

```
没有代理：
你 →（直接寄信）→ google.com   ❌ 信被海关拦截

有代理：
你 → 代理软件 → 海外服务器 → google.com   ✅ 代理帮你转发
```

代理软件（Clash、V2Ray 等）通常跑在你的 Windows 上：

1. 它在 `127.0.0.1:17891` 开一个"代购窗口"
2. 你的程序把请求交给它
3. 它转交给海外的服务器
4. 海外服务器拿到内容，原路返回

**关键点**：想让程序走代理，程序必须**知道**代理在哪儿。两种告知方式：

1. **环境变量**：程序启动时告诉它 `http_proxy=127.0.0.1:17891`
2. **命令行参数**：运行程序时直接传 `--proxy 127.0.0.1:17891`

## 9. WSL2 的本质：一台装在 Windows 里的虚拟机

这是理解你所有 WSL 网络问题的核心。

**WSL2 不是"Windows 里的一个软件"，它是一台完整的虚拟机**——Hyper-V 技术在 Windows 里隔离出一台虚拟电脑，里面跑着真正的 Linux 内核。

```
┌────────────────────────────────────────────┐
│ Windows 主机（真实电脑）                      │
│  ├─ 代理软件在 127.0.0.1:17891 开着窗口      │
│  ├─ 真实网卡：192.168.1.5                   │
│  └─ Windows 的 127.0.0.1                    │
│                    │                        │
│            ┌───────┴────────┐               │
│            │  NAT 虚拟网关   │ ← 虚拟路由器    │
│            └───────┬────────┘               │
│  ┌─────────────────┴─────────────────────┐  │
│  │ WSL2 虚拟机（另一台"电脑"）              │  │
│  │  ├─ WSL 的 127.0.0.1 ← 指向 WSL 自己   │  │
│  │  └─ WSL 的内网 IP：172.x.x.x           │  │
│  └───────────────────────────────────────┘  │
└────────────────────────────────────────────┘
```

这带来一个巨大的坑：

> **WSL 里的 `127.0.0.1` 指的是 WSL 虚拟机自己，不是你的 Windows！**

所以如果你没开镜像网络模式：

```
你在 WSL 里访问 127.0.0.1:17891
→ 访问的是 WSL 虚拟机自己的 17891 端口
→ 但代理软件跑在 Windows 上！
→ 连接被拒绝（Connection refused）
```

这就是"为什么 WSL 里用 Windows 上的代理这么麻烦"的根本原因——**中间隔着一堵虚拟机的墙**。

而且，WSL2 的网络还叠加了一层 NAT（网络地址转换）：WSL 发出的所有请求都要经过 Windows 转一手。这层转换历史悠久、毛病不少，尤其对 IPv6 的支持很差。

**你 WSL 网络问题的根源总结**：

| 问题 | 原因 |
|------|------|
| 访问不到 Windows 上的服务（代理、数据库） | 127.0.0.1 各指各的 |
| 时不时连不上网 | NAT 转换层偶发故障 |
| 网络慢 | 每个包都要多绕一层 Windows 转发 |
| IPv6 相关卡顿 | NAT 对 IPv6 的模拟不可靠 |

## 10. 镜像网络模式：拆掉虚拟机之间的墙

Windows 11 提供了一个叫 **镜像网络（Mirrored Networking）** 的模式，写在 `C:\Users\你的用户名\.wslconfig` 里：

```ini
[wsl2]
networkingMode=Mirrored
```

开启后，WSL2 不再躲在 NAT 后面，而是**直接共享 Windows 的网络栈**：

- WSL 里的 `127.0.0.1` **就是** Windows 的 `127.0.0.1`
- WSL 的 IP 地址和 Windows 一样
- 代理软件开的窗口，WSL 直接可见

**你已经开启了这个模式**，这就是为什么你 shell 里的 `http_proxy=127.0.0.1:17891` 能正常工作——curl、wget、pip 都能走代理。

但要注意：镜像网络解决了"找不找得到代理"，**没有解决 IPv6 的问题**。WSL2 的 IPv6 数据通路即使镜像了也不如 IPv4 稳定（这是 WSL 的已知问题）。

## 11. 环境变量：程序启动时收到的"便条"

程序启动时，操作系统会给它一批"便条"，上面写着各种配置信息。这些便条叫**环境变量**。

你的 shell 配置里就有这样的便条：

```bash
http_proxy=http://127.0.0.1:17891    # 便条1：代理在 127.0.0.1 的 17891 房间
https_proxy=http://127.0.0.1:17891   # 便条2：加密流量也走这个代理
```

程序要不要看这些便条，取决于程序自己：

- **curl、wget、pip、git** → 会读便条 → 自动走代理 ✅
- **apt** → 在 Ubuntu 24.04 下，**不会**读 `http_proxy` 便条（它只认自己的配置文件 `/etc/apt/apt.conf.d/` 和命令行参数）❌
- **Chrome** → 不读这些便条，走系统设置 ❌

所以同样的便条，不同的程序反应不同。这就是为什么 curl 能翻墙而 apt 不行——**不是网络坏了，是程序没看便条**。

## 12. sudo 和 env_reset：为什么便条会丢

Linux 里，普通用户权限有限。安装软件等系统级操作要用 `sudo`（以管理员身份运行）。

但 sudo 有个安全设计叫 **env_reset（环境重置）**：为了安全，sudo 在运行命令前会**清空大部分环境变量**。

```
你在终端：sudo apt-get install xxx
              │
              ▼
sudo 检查你的环境变量：
  http_proxy=127.0.0.1:17891   ← 被清掉（env_reset）
  PATH=/usr/bin/...            ← 被保留（白名单）
              │
              ▼
apt 启动时看到的便条：干干净净，没有代理信息
              │
              ▼
apt 不知道有代理 → 直连 archive.ubuntu.com
```

**为什么 sudo 要这么做？** 防止有人通过伪造环境变量来提权攻击。比如攻击者把一个假的 `PATH` 传给你 sudo 运行的命令，让你执行恶意程序。这是安全设计，不是 bug。

## 13. 完整复盘：你的 apt 卡住事件

现在把前面所有知识串起来，还原你遇到的问题：

### 事件经过

```bash
# 你在 WSL 终端执行：
sudo apt-get install -y qt6-base-dev cmake g++
# 结果：卡在 0% [Waiting for headers]
```

### 逐步分析

**第 1 步：sudo 清掉了代理便条**

你的 shell 有 `http_proxy=127.0.0.1:17891` 的便条，但 sudo 的 env_reset 把它清掉了。apt 启动时**根本不知道代理的存在**。

**第 2 步：apt 尝试直连**

apt 心想："没有代理配置，那我直接连 archive.ubuntu.com 吧。"

**第 3 步：DNS 解析给出两个地址**

apt 查到 archive.ubuntu.com 同时有 IPv4 和 IPv6 地址。apt 优先尝试 IPv6。

**第 4 步：IPv6 通路不可靠**

WSL2 的 IPv6 是模拟的。TCP 连接能建立（"敲门有人应"），但实际数据传输不通（"开门后不说话"）。apt 发出请求，永远等不到响应头 → `0% [Waiting for headers]`。

**第 5 步：你换了方案 2**

```bash
sudo apt-get install \
  -o Acquire::http::Proxy="http://127.0.0.1:17891" \
  -o Acquire::ForceIPv4=true \
  -y qt6-base-dev cmake g++
```

| 参数 | 破解的问题 | 原理 |
|------|-----------|------|
| `Acquire::http::Proxy=...` | 第 1 步（便条被清） | 代理地址写在**命令行参数**里，sudo 清不掉命令行参数 |
| `Acquire::ForceIPv4=true` | 第 3-4 步（IPv6 卡住） | 强制 apt 只用 IPv4，绕开不可靠的 IPv6 通路 |

**第 6 步：成功**

apt 知道代理在 `127.0.0.1:17891`（镜像网络模式下，这个地址直达 Windows 上的代理），走 IPv4 本地回环把请求交给代理，代理用自己的客户端去抓包（Windows 侧的 IPv6 处理正常），一切通畅。

### 一张图看懂

```
❌ 失败路径：
apt →（不知道代理）→ 直连 → IPv6 → NAT 模拟 → 数据不通 → 卡死

✅ 成功路径：
apt → 127.0.0.1:17891 → Windows 上的代理 → 海外服务器 → 数据到手
      (命令行参数告知)   (镜像网络直达)     (代理负责真正的抓包)
```

## 14. 日常排查清单

以后 WSL 网络出问题，按这个顺序排查：

### ① 先问：是"找不到"还是"连不通"？

```
Connection refused → 目标端口没人在听（服务没启动，或 127.0.0.1 指错了电脑）
Timeout → 通路有问题（防火墙、NAT、IPv6 模拟故障）
DNS 解析失败 → 查号台问题（DNS 配置错、代理没接管 DNS）
```

### ② 检查 WSL 是否开启了镜像网络

```bash
cat /mnt/c/Users/$USER/.wslconfig
# 期望看到：networkingMode=Mirrored
```

### ③ 检查代理是否可达

```bash
timeout 3 bash -c "echo > /dev/tcp/127.0.0.1/17891 && echo 代理可达 || echo 代理不可达"
```

### ④ 检查目标网站是否可达

```bash
# 走代理
curl -x http://127.0.0.1:17891 -I https://www.google.com

# 直连
curl -I https://archive.ubuntu.com
```

### ⑤ apt 专用的两板斧

```bash
# 板斧1：显式指定代理 + 强制 IPv4
sudo apt-get install -o Acquire::http::Proxy="http://127.0.0.1:17891" -o Acquire::ForceIPv4=true xxx

# 板斧2：永久写入配置（一劳永逸）
sudo tee /etc/apt/apt.conf.d/99proxy <<'EOF'
Acquire::http::Proxy "http://127.0.0.1:17891";
Acquire::https::Proxy "http://127.0.0.1:17891";
Acquire::ForceIPv4 "true";
EOF
```

### ⑥ 其他程序走代理的通用方式

```bash
# 临时（当前终端生效）
export http_proxy=http://127.0.0.1:17891
export https_proxy=http://127.0.0.1:17891

# 永久（写入 ~/.bashrc）
echo 'export http_proxy=http://127.0.0.1:17891' >> ~/.bashrc
echo 'export https_proxy=http://127.0.0.1:17891' >> ~/.bashrc
source ~/.bashrc
```

## 结语

你的 WSL 网络问题之所以"复杂"，不是因为你操作有误，而是 WSL2 的架构天然把网络分成了两半：**Windows 一半，WSL 一半**。中间任何一环（sudo 清变量、IPv6 模拟、代理位置）出问题，都表现为"网络断了"。

但拆开看，每一环都有明确的检查方法。下次再遇到问题，就从第 14 节的清单开始，一步步定位到具体哪一环断了。
